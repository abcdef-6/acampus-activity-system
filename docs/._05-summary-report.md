# 校园活动报名与签到管理系统 - 实验总结报告

## 一、项目背景与小组分工
本项目模拟“校园活动报名与签到管理系统”的开发前管理组织工作。小组实际由1人完成，采用单人双账号方式模拟两名成员：
- **zhangsan**（模拟）：项目经理、计划负责人，负责WBS分解、进度计划编制、初始仓库搭建。
- **lisi**（模拟）：配置管理员、协作成员，负责配置管理方案、分支策略、冲突制造与解决。

## 二、WBS分解结果及三级分解逻辑
按照交付物导向原则，WBS分解到三级：
- 一级：项目管理成果、业务功能成果（占位）。
- 二级：仓库与基础设施、范围计划文档、进度计划文档、配置管理文档、总结报告等。
- 三级：可管理的最小成果单元，如“创建远程仓库”“编制WBS”“确定工期与前置关系”等。

逻辑：从最终交付物反推所需工作，避免以“开会、讨论”等动作为主线。

## 三、简化进度计划及关键安排依据
从WBS中提取关键活动形成进度计划表（见 `02-schedule.md`）。工期按实验学时（8学时）折算，0.5天对应1学时。前置关系依据活动之间的自然依赖（如必须先有WBS才能提取关键活动）。责任人分配体现模拟双人协作。

## 四、配置项识别、分支策略、提交与合并规则
- **配置项**：包括README、各文档、冲突示例文件等。
- **分支策略**：`main` 为生产分支，`feature/*` 用于所有开发/文档编写，合并前需解决冲突。
- **提交规范**：采用 `<type>: <subject>` 格式。
- **合并规则**：feature 分支合并到 main 前须无冲突，并由非作者确认（模拟）。

详见 `03-config-management.md`。

## 五、冲突制造、识别与解决过程
1. **制造冲突**：在 `docs/conflict.md` 第二行，zhangsan 和 lisi 分别修改为不同内容，基于同一 `main` 提交创建两个 feature 分支。
2. **合并顺序**：先将 zhangsan 的分支合并到 main（无冲突），再将 lisi 的分支合并到 main（产生冲突）。
3. **解决冲突**：Git 标记冲突位置后，手动编辑文件，删除冲突标记，保留最终内容。
4. **提交解决**：`git add`、`git commit`、`git push`，合并提交作者为 lisi（解决冲突者）。

冲突解决后的最终版本保留了双方修改的整合内容。

## 六、实验收获与问题
- **收获**：掌握了 Git 分支管理、冲突解决、WBS 三级分解、进度计划编制等项目管理技能。
- **问题**：单人模拟双账号时需注意两个工作区的身份配置（`git config user.name`）和凭据管理（使用 token 避免认证失败）。VSCode 打开文件夹时需选择“打开文件夹”而非直接点击目录。
- **反思**：软件项目管理中，版本控制与文档管理同等重要，清晰的协作约定能有效减少冲突。
