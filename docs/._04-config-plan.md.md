# 配置管理方案

## 1. 识别的主要配置项
- `README.md`                         : 项目概况与协作约定
- `docs/01-wbs.md`                    : 三级WBS分解
- `docs/02-schedule.md`               : 简化进度计划
- `docs/03-config-management.md`      : 配置管理方案
- `docs/conflict.md`                  : 用于制造冲突的示例文件
- `docs/05-summary-report.md`         : 实验总结报告

## 2. 分支策略
- `main`：生产分支，受保护，仅允许通过PR合并，必须经过代码审查（模拟）。
- `dev`：集成分支（本实验可省略，直接用feature → main）。
- `feature/*`：所有新功能或文档修改从此分支创建，命名格式为 `feature/简短描述`。

## 3. 提交规范
格式：`<type>: <subject>`
- `docs`   : 文档相关（如 `docs: 添加WBS`）
- `feat`   : 功能相关（模拟业务功能时使用）
- `fix`    : 修复错误
- `chore`  : 杂项（如初始化、配置修改）
- `refactor`: 重构（不改变功能）
- `merge`  : 合并分支

示例：`docs: 更新进度计划`

## 4. 合并规则
- feature 分支合并到 main 之前，必须确保无冲突。
- 合并前需在本地或远程进行简单审查（模拟）。
- 重要文档（如总结报告）需由非作者进行确认。

## 5. 版本标记
每个实验阶段完成后打标签，例如：
- `v1.0-wbs`         : 完成WBS文档
- `v1.1-schedule`    : 完成进度计划
- `v2.0-config`      : 完成配置管理方案
- `v3.0-conflict`    : 完成冲突解决
- `v4.0-summary`     : 完成总结报告

## 6. 冲突解决流程
1. 两个不同分支修改同一文件相同行。
2. 合并时Git提示冲突。
3. 手动编辑冲突文件，删除`<<<<<<<`、`=======`、`>>>>>>>`标记，保留最终内容。
4. 执行 `git add`、`git commit` 完成合并。
5. 推送至远程分支。
