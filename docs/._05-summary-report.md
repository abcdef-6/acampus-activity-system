一、实验目的

1）掌握基于Git的版本管理与团队协作流程：通过实际操作，深入理解分布式版本控制系统的工作原理，熟悉包括仓库创建、分支管理、代码提交、拉取请求、合并冲突解决等在内的完整团队协作流程。
2）能够围绕交付物进行三级WBS分解，制定简化进度计划：学习以“结果/可交付物”为导向的工作分解结构方法，将项目目标逐级分解至可管理的工作单元，并依据WBS识别关键活动，建立带有依赖关系和责任人的项目进度计划。
3）识别配置项，制定分支策略，完成分支合并与冲突解决：明确项目中需要进行版本管理的核心配置项，设计符合团队协作模式的分支管理策略，并有能力模拟、分析和解决分支合并过程中产生的代码冲突。
4）通过双人协作实践，理解软件项目管理中的范围、进度与配置管理：在模拟的真实协作环境中，体验范围界定、进度规划与配置管理三大知识领域在项目执行过程中的相互作用与重要性。

三、项目背景

“校园活动报名与签到管理系统”是一个典型的业务支持型软件项目，旨在为学校提供一套完整的线上活动组织工具，核心功能涵盖活动发布、学生报名、名单审核、二维码签到及签到数据统计导出。需要特别说明的是，本次实验的核心目标并非完整实现上述业务系统的前后端代码，而是围绕项目管理过程中的关键交付物——包括工作分解结构、进度计划、配置管理方案及总结报告——进行版本控制与协作流程的演练，以此来强化项目管理方法论与工具实践的融合。

七、配置管理方案

7.1 主要配置项识别
配置项是项目中需要受控的产品、文档或数据。本项目的核心配置项及其路径如下：
README.md：项目元信息、团队介绍与协作约定。
docs/01-wbs.md：三级WBS的详细文档。
docs/02-schedule.md：项目进度计划。
docs/03-config-management.md：本配置管理方案。
docs/conflict.md：用于演示和练习冲突解决的文件。
docs/05-summary-report.md：项目总结报告。


7.2 分支策略设计
main 分支：稳定、可交付的版本线。所有开发成果最终必须通过拉取请求或本地合并方式集成至此分支。此分支被设置为GitHub受保护分支，禁止直接推送。
feature/* 分支：从 main 分支派生，用于单个功能点或文档的开发。命名规则为 feature/<简短描述>，例如 feature/schedule-plan。完成开发并测试无误后，合并回 main 分支并删除。


7.3 提交信息规范
所有提交信息必须遵循 类型: 简短描述 格式：
docs: 更新WBS文档中的活动描述
feat: 添加冲突示例文件的初始版本
merge: 合并feature/summary-report分支至main
chore: 更新.gitignore以排除.DS_Store文件


7.4 合并与冲突解决规则
合并前同步：在执行 git merge 操作之前，必须先在自己的分支上执行 git pull origin main（假设要合并到main），将最新的远程 main 分支更改拉取到本地。
冲突定位：若合并过程中Git提示冲突，使用 git status 查看冲突文件列表。
冲突解决：在编辑器中打开冲突文件，查找并理解 <<<<<<<， =======， >>>>>>> 标记的内容。与相关成员协商后，删除标记并编辑文件为最终正确内容。
提交合并结果：解决冲突后，执行 git add <冲突文件> 标记为已解决，然后执行 git commit（Git通常会生成一个默认的合并提交信息），最后 git push 推送合并后的分支。
八、冲突制造与解决过程（实操记录）

8.1 冲突制造步骤 (模拟并行修改)
1.建立基线 (刘佰雄)：在 main 分支上创建文件 docs/conflict.md，初始内容为：

# 冲突测试文件这是初始内容，团队将基于此版本进行并行修改。
提交并推送到远程 main 分支。

成员A的修改 (刘佰雄)：
基于 main 分支创建新分支 feature/liu-conflict。
将文件第二行修改为：刘佰雄修改了这一行，增加了新的数据定义: int activityId = 100;。
提交更改并推送 feature/liu-conflict 分支。
切换回 main 分支，将 feature/liu-conflict 合并进来。此操作无冲突，并推送更新后的 main。

成员B的修改 (阿卜杜卡哈尔)：
关键点：在刘佰雄执行合并 之前，阿卜杜卡哈尔就已经基于旧的 main 分支（即步骤1的基线版本）创建了自己的分支 feature/abdu-conflict。
他在此分支上将同一文件的第二行修改为：阿卜杜卡哈尔修改了这一行，定义了签到记录: checkinId = 5000;。
提交更改并推送 feature/abdu-conflict 分支。

冲突产生：现在，阿卜杜卡哈尔在自己的本地环境中，先切换回 main 分支，执行 git pull 获取最新的远程 main（该分支已包含刘佰雄的修改）。然后，他执行 git merge feature/abdu-conflict。此时，因为 main 分支和 feature/abdu-conflict 分支修改了文件的同一行，Git无法自动合并，冲突成功产生。

8.2 冲突解决过程
1.定位冲突：Git提示 Auto-merging docs/conflict.md 和 CONFLICT (content): Merge conflict in docs/conflict.md。使用 git status 确认冲突文件。
2.编辑冲突文件：打开 docs/conflict.md，内容如下：

# 冲突测试文件<<<<<<< HEAD刘佰雄修改了这一行，增加了新的数据定义:int a = 99955; int b = 11500;;=======阿卜杜卡哈尔修改了这一行，定义了整数: int a = 50000; int b = 600;>>>>>>> feature/abdu-conflict
协商并解决：两位成员通过即时通讯工具沟通，认为这两个定义都有用，应同时保留。最终决定将冲突块修改为：
# 冲突测试文件合并后结果：
int a = 99955; int b = 11500;
int a = 50000; int b = 600;

提交合并：
执行 git add docs/conflict.md。
执行 git commit -m "merge: 解决conflict.md冲突，合并双方的活动ID和签到记录ID定义"。
执行 git push origin main。

九、实验收获与问题

9.1 主要收获
工具掌握：熟练掌握了Git的核心操作，特别是分支管理、冲突解决、交互式变基等高级特性，理解了其内部原理（如HEAD、暂存区、对象库）。

方法论应用：深刻理解了WBS“结果导向”的分解原则，并能将其转化为可执行的进度计划。学会了从项目管理者的视角进行配置项识别和策略设计。

协作认知：通过双人实战，亲身体验了分布式版本控制如何支撑“异步”、“并行”的团队协作，并认识到清晰、严格的协作规范是避免混乱的基石。

9.2 遇到的问题与解决方案
问题1: Git推送认证失败：初次使用GitHub时，因密码方式被废弃导致 git push 失败。
解决：改用个人访问令牌代替密码进行HTTPS操作认证。生成令牌时需授予 repo 和 workflow 等必要权限。


问题2: 冲突未按预期出现：按照计划制造冲突时，Git自动合并了修改而没有提示冲突。
原因分析：第二个分支在创建时，其基础版本并非第一个分支合并后的最新 main，或者两人修改了文件的不同行/不同区域。

解决：严格复现流程：①创建基线并推送；②成员A创建分支、修改、合并回main并推送；③成员B在成员A合并之前，就基于原始的基线提交创建分支并修改同一行。这确保了历史产生“分叉”。

问题3: VSCode中Git操作偶发报错。

解决：不依赖图形界面的“自动操作”，转而使用内置终端执行Git命令，增加了操作的透明度和可控性。同时清理了Windows凭据管理器中的旧GitHub凭据，避免冲突。

9.3 反思与改进
1）双人协作应提高同步频率，建议在开始一项新任务前和执行关键合并前，都执行一次 git pull，以减小冲突范围。

2）制造冲突实验的关键在于理解Git的合并基础（merge base）。第二个分支必须从第一个分支修改前的节点分叉出去。

3）本次实验的分支策略相对简单，未来在更复杂的项目中，可引入 develop、release、hotfix 等更精细的分支模型（如Git Flow）。





十、实验总结
本次实验完整地模拟了一个小型软件项目的管理过程，从范围计划（WBS）、进度计划到配置管理和版本控制协作，所有核心交付物均通过Git进行管理，并托管于GitHub平台。项目成功执行了分支策略，并故意制造、分析、解决了代码合并冲突，加深了对分布式协作本质的理解。所有文档均按计划提交至 main 分支，提交历史清晰、规范、可追溯。实验不仅达成了预设的教学目标，还为团队成员在未来真实、复杂的软件工程项目中，应用项目管理知识体系和高效协作工具奠定了坚实的基础。
